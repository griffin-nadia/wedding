## 0. Stop the 19 Oct outage happening again

### Incident note: 19 Oct 2026

- **Cause:** the web app and the email queue run as the wedding account. A back-end push added permission scopes the
  wedding account hadn't approved, so `SpreadsheetApp.getActive()` threw "You do not have permission…
  spreadsheets.currentonly || spreadsheets" (in `sheet_`, from `getHousehold_` and `flushQueue`).
- **Impact:** for hours every guest link showed "That link doesn't look right". The back end answered
  `{ ok: false, code: "read_failed" }`; the site read the missing household as "we don't know this link", wiped the
  guest's saved copy and showed the bad-link page. Queued emails waited. No data was lost.
- **Fix:** Jehan approved the scopes from the wedding account. Health went back to `sheet: true`, pending 0.
- **Prevention (this section):**
  - The scopes are declared in `apps-script/appsscript.json` (7, the ones the code already used, so nothing new to
    approve). `scripts/scopes-check.mjs` (in `npm test`, so in the gates) fails when the code needs a scope that isn't
    declared, with "new scope: approve it as the wedding account (run health_ once) before deploying".
  - `scripts/deploy-apps-script.sh` is the one deploy path (docs/deploy.md): fresh main, the scopes check, a stop if
    the declared scopes changed since the last deploy (until `--scopes-approved`), clasp push, the existing deployment
    updated, then `?action=health` must answer ok or it fails loudly.
  - `sheet_()` opens the sheet by ID (`SHEET_ID` in Script Properties), falling back to the bound sheet.
  - The site: a back-end error is "We're having a little trouble, try again in a few minutes", never "That link
    doesn't look right", and never wipes the saved copy. A copy from the last 24 hours still shows the invite (read
    only). Covered in `scripts/stress-api.mjs` (no copy, a copy from an hour ago, one from two days ago).
  - Alerts at once: `watchHealth` every 15 minutes (the sheet won't open, or the queue has stopped), and the queue
    failing 3 runs in a row. The wedding account's own queue turns the watch on the first time it runs.
  - UptimeRobot's keyword monitor on `?action=health` for `"ok":true` ([monitoring.md](../monitoring.md)), for the
    case where Google won't run the script at all.
- Also fixed on the way: two stale checks in `scripts/stress-api.mjs` (the FAQs' "Ask us" button and the flat map's
  class), 19 of 19 pass.
